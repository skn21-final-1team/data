# Comparison CSV 지표 해석 가이드

`comparison.csv`는 동일 문서에 대해 여러 청킹 전략의 결과를 한눈에 비교하는 파일이다.

## 전략 (strategy)

| strategy 패턴 | 기법 | 설명 |
|---|---|---|
| `헤더기반_MarkdownHeader` | MarkdownHeaderTextSplitter | `#`, `##`, `###` 헤더를 기준으로 섹션 단위 분할. chunk_size 무시 |
| `재귀분할_Recursive_{N}c` | RecursiveCharacterTextSplitter | `\n\n` → `\n` → ` ` 순서로 구분자를 시도하며 N자 이내로 분할 |
| `MD구분자_Markdown_{N}c` | MarkdownTextSplitter | 마크다운 구분자 우선 사용 + N자 제한. Recursive와 Header의 중간 |
| `토큰기반_Token_{N}tok` | TokenTextSplitter (cl100k_base) | 문자가 아닌 토큰 수 기준 분할. 임베딩 토큰 제한에 정확히 맞출 때 유용 |

## 기본 통계 지표

| 컬럼 | 의미 | 판단 기준 |
|---|---|---|
| `chunks` | 총 청크 수 | 너무 많으면 검색 노이즈, 너무 적으면 정보 손실 |
| `avg_chars` | 평균 청크 길이 (문자) | 임베딩 모델 max token에 맞는 범위 (보통 300~1000자) |
| `min_chars` | 최소 청크 길이 | 50자 미만이면 의미 없는 청크 존재 가능 |
| `max_chars` | 최대 청크 길이 | 임베딩 모델 토큰 제한 초과 여부 확인 |
| `std_chars` | 표준편차 | **낮을수록 좋음** — 청크 크기가 균일 |

## 구조 보존 지표 (핵심)

| 컬럼 | 의미 | 판단 기준 |
|---|---|---|
| `header` | 원본 헤더가 청크에 보존된 비율 | **1.0에 가까울수록 좋음** — 문맥 유지에 중요 |
| `code` | 코드 블록이 깨지지 않은 비율 | **1.0 필수** — 깨진 코드 블록은 검색 품질 저하 |
| `table` | 테이블이 깨지지 않은 비율 | **1.0 필수** — 깨진 테이블은 무의미 |
| `list` | 리스트가 온전히 포함된 비율 | **높을수록 좋음** |
| `coverage` | 원본 대비 청크 합산 문자 비율 | **0.95~1.0** — 1.0 초과면 중복, 0.9 이하면 손실 |
| `boundary` | 문장/문단 경계에서 청크가 나뉜 비율 | **높을수록 좋음** — 문장 중간 절단은 검색 품질 저하 |

## 기타

| 컬럼 | 의미 |
|---|---|
| `time_s` | 처리 시간 (초). 참고용 |

## 최적 전략 선택 우선순위 (RAG 관점)

1. **code, table = 1.0** 인지 먼저 확인 (구조 깨지면 탈락)
2. **coverage ≈ 0.95~1.0** 정보 손실 없는지 확인
3. **boundary 높은 것** 선택 (검색 정확도 직결)
4. **header 높은 것** 선택 (문맥 보존)
5. **std_chars 낮은 것** 선택 (균일한 청크 → 안정적 임베딩)
6. avg_chars가 임베딩 모델 토큰 제한 내인지 확인

이 단계에서 2~3개 후보를 추리고, 최종 판단은 임베딩 후 retrieval 성능(실제 질의 응답)으로 결정한다.
